Bachelor thesis · DTU REMANUFACTORY

Automated Gantry-Based Disassembly System

Context
Bachelor thesis, 2026
Team
2 engineers
Supervisor
Tobias Eifler
My focus
Mechanics, sensing & control

Remanufacturing recovers value from worn-out products by taking them apart so their components can be reused — but that disassembly is still done almost entirely by hand, because every incoming product is a little different. My bachelor thesis, carried out with DTU's national REMANUFACTORY research centre, asked whether a single machine could automate the repetitive part of that work while still handing the tricky cases back to a person.

The answer was a unified tool head: one 3D-printed module, driven through a single shaft, that both unscrews fasteners and presses parts out without ever swapping tools. That is harder than it sounds, because the same assembly has to transmit rotational torque for screwing and axial force for pressing at the same time. We solved it with an internal spring that lets the head pass passively from screw mode into press mode as it pushes down — no motor, no reconfiguration — and even changes its own screwdriver bits at a small parking station using only the machine's existing axes.

Making it reliable was really a sensing and software problem. A camera finds every screw, corrects for lens distortion and viewing angle with a homography calibration, and reports each screw's position in millimetres and its size (M4 vs M5). A laser distance sensor watches the head descend and can tell ordinary surface contact apart from the tiny extra travel that means the bit has actually seated in the screw. A load cell monitors the press force and stops immediately at a set limit. All of it is coordinated by a state machine that, at every step, checks the sensors and either continues, retries, or flags the part for a human — the machine never pushes blindly.

We deliberately built the prototype in 3D-printed PLA so a failed part could be redesigned and reprinted the same day, but dimensioned every component so the exact same geometry can be re-cut in 10 mm metal plate for a stronger production version, without moving a single sensor. Course 34721 · Linear Control Design

REGBOT Self-Balancing Robot

Context
Course project, 2026
Team
4 engineers
Domain
Classical control
Tools
MATLAB · Simulink

A REGBOT is a two-wheeled robot that has to actively balance to stay upright — like a Segway the size of a lunchbox. Left alone it simply falls over; the only thing keeping it up is a controller adjusting the wheels hundreds of times a second. For this control-design course we designed and tuned the complete control system that keeps it balanced while it drives and moves to target positions.

The system is built as four nested control loops, each wrapped around the one inside it: a fast inner loop regulating wheel speed, a balance loop that holds the tilt angle, then a velocity loop, and finally a position loop on the outside. We designed each one in the frequency domain — choosing a target phase margin, reading the response straight off Bode plots, and sizing the controller from there — then modelled and linearised the whole robot in MATLAB and Simulink to check the design before it ever touched hardware.

Balancing is fundamentally unstable, so the tilt dynamics needed a post-integrator just to become controllable, and a PI-Lead controller on top to hold the angle without overshooting. The robot also has a quirk called non-minimum-phase behaviour — to drive forward it first tips backward a little — which we tamed with a pre-filter that eases each command in gently.

The most instructive part was the gap between theory and reality. The clean simulated design misbehaved on the real robot, so we hand-tuned every loop on the hardware and learned exactly which effects — friction, time delays, sensor noise — the tidy linear model had quietly left out. The finished robot balanced through a full closed square-path mission. Watch the full mission run →

  • Cascaded controller stack. PI wheel-speed loop, a post-integrator to stabilise the inherently unstable tilt, a PI-Lead balance controller, and P position control.
  • Undershoot handling. Added a first-order pre-filter to tame the robot's non-minimum-phase response so the balance loop had time to react.
  • Simulation vs. hardware. Directly compared modelled and measured step responses, then reconciled them through tuning.
  • Full mission. The finished robot balanced while completing a closed square-path driving mission.
Technical skills
  • Classical control design — frequency-response methods, phase margin, lead/lag compensation and cascaded loop architecture.
  • Modelling & simulation — MATLAB/Simulink linearisation of an unstable plant.
  • Theory-to-hardware transfer — diagnosing why a robot behaves differently than its model and closing the gap methodically.
Ways of working

  • Splitting a four-person control problem into loops the team could design in parallel.
Course 41801 · Project work

AI Robotic Arm for Waste Sorting

Context
Project work, 2025
Team
5 engineers
Supervisor
Konstantinos Poulios
Tools
SolidWorks · IKPy · OpenAI

This is a 5-axis robotic arm that sorts waste on its own, aimed at the kind of manual, and often unsafe, sorting done in low-resource areas. A camera looks down at the work area, an AI model identifies what each object is, and the arm picks it up and drops it in the right bin — for example separating electronic waste from everything else.

Before any building, we chose the concept properly. A morphological analysis compared grippers and drive options, and a torque calculation (a peak of roughly 6.7 N·m at the shoulder) showed that affordable stepper motors simply couldn't lift the target load — so the arm is servo-driven, with each joint's motor sized to what that joint actually has to hold. The whole structure is 3D-printed, designed with the tolerances the printer can really hold.

To make the tip reach a chosen point in space, we used inverse kinematics — the maths that works out every joint angle from a desired end position. We fed the IKPy library a URDF robot model exported from our SolidWorks CAD, while a Raspberry Pi camera (calibrated against ArUco markers) converts what it sees into real-world X-Y coordinates for the arm to aim at. An AI image-recognition model then labels the object so the arm knows which bin it belongs in.

Two problems taught us the most, and both lived on the messy boundary between the digital model and the physical robot. First, the servos didn't actually go where they were told — each had its own offset and scaling — which we fixed with a measured per-motor calibration function that translates the computed angle into the correct command. Second, the servos' 180° limits kept trapping the solver in dead-ends, so we moved those limits out of the model and handled them in our own code by seeding the solver with sensible starting guesses.
